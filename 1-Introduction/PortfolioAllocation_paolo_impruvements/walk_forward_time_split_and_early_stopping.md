# Walk-forward, time splits, and early stopping — how the data is partitioned

This document explains exactly how the pipeline partitions the historical data into training, validation, and test slices, and how early stopping uses the validation slice to pick the best model checkpoint. It applies to folders 5 onward (where early stopping is enabled). Folders 3–4 use walk-forward without early stopping, so the validation slice doesn't exist there.

## The three slices, by name

There are THREE distinct data slices the pipeline cares about, each with a different purpose. They are non-overlapping in time.

| Slice              | What it's for                                    | Used by which stage                     |
|---|---|---|
| train_only         | Gradient updates (the model literally trains on this) | Stage 2 only                         |
| validation (val)   | Periodic Sharpe check during training, to pick the best model checkpoint | Stage 2 only — never reported as a result |
| eval (OOS test)    | Out-of-sample backtest used to compute headline metrics | Stage 3 (and downstream stages 4/5) |

In folders without early stopping (0–4), there is no validation slice — only train and eval. In folder 5 onward, train is further split into train_only and validation.

## The walk-forward outer loop

`walk_forward.auto` in `config.json` controls how the whole timeline is chopped into overlapping windows:

```
"walk_forward": {
  "enabled": true,
  "auto": {
    "train_years": 6,
    "eval_years":  1,
    "step_years":  1
  }
}
```

Each window is a 4-tuple `(train_start, train_end, eval_start, eval_end)` generated by `expand_walk_forward_windows()` in `utils.py`. The sliding rule:

- Start with `train_start = data.train_start_date` (default 2009-01-01).
- `train_end = train_start + train_years`.
- `eval_start = train_end`.
- `eval_end = min(eval_start + eval_years, data.trade_end_date)`.
- Advance: `train_start += step_years`.
- Repeat until `eval_start >= data.trade_end_date`.

With the defaults you get 7 windows:

| Window | Train start | Train end  | Eval start | Eval end   |
|---|---|---|---|---|
| 0      | 2009-01-01  | 2014-12-31 | 2015-01-01 | 2015-12-31 |
| 1      | 2010-01-01  | 2015-12-31 | 2016-01-01 | 2016-12-31 |
| 2      | 2011-01-01  | 2016-12-31 | 2017-01-01 | 2017-12-31 |
| 3      | 2012-01-01  | 2017-12-31 | 2018-01-01 | 2018-12-31 |
| 4      | 2013-01-01  | 2018-12-31 | 2019-01-01 | 2019-12-31 |
| 5      | 2014-01-01  | 2019-12-31 | 2020-01-01 | 2020-12-31 |
| 6      | 2015-01-01  | 2020-12-31 | 2021-01-01 | 2021-10-31 |

The 7 eval slices stitched together cover **2015-01-01 → 2021-10-31** continuously — about 6.8 years of out-of-sample testing.

Critical no-look-ahead property: each window's eval period is strictly AFTER its train_end. The model used to backtest 2015 has only seen 2009–2014 data.

## The inner split: train_only and validation

When `early_stopping.enabled = true`, the WINDOW's training slice is further split BEFORE training starts:

```python
def split_train_validation(train_df, val_fraction=0.1):
    dates = pd.Index(train_df["date"].unique()).sort_values()
    n_val = max(int(round(len(dates) * val_fraction)), 1)
    cut_date = dates[len(dates) - n_val]
    train_only = train_df[train_df["date"] <  cut_date]   # first 90% of dates
    validation = train_df[train_df["date"] >= cut_date]   # last 10% of dates
    return train_only, validation
```

The validation slice is **the last `val_fraction` of the window's training dates**. It is INSIDE the window's training range, NOT inside the eval range.

For window 0 with `val_fraction = 0.1`:

| Slice        | Date range                  | # trading days  | Role                                                         |
|---|---|---|---|
| train_only   | 2009-01-02 → ~2014-06-30    | ~1360 (90%)     | Where PPO computes gradients                                 |
| validation   | ~2014-07-01 → 2014-12-31    | ~152 (10%)      | ES rolls policy through this every 5000 timesteps            |
| eval (test)  | 2015-01-01 → 2015-12-31     | ~252            | Stage 3 OOS backtest — NEVER seen in stage 2                 |

Three time-ordered, non-overlapping periods. The model sees its training data, gets periodically evaluated on a held-out slice from the same era, and is finally tested on a fresh year after that.

## How early stopping uses the validation slice

`ValidationSharpeCallback` is attached to `model.learn()` in stage 2. On every `eval_freq` training timesteps (default 5000):

1. Build a fresh env on `val_df`.
2. Roll the current policy through it deterministically — one full pass over the validation period.
3. Capture `portfolio_return_memory` from the env (the realised daily returns over the val period).
4. Compute annualised Sharpe: `sqrt(252) * mean(returns) / std(returns)`.
5. If Sharpe improved by ≥ `min_delta` (default 0.01) compared to the best-so-far, save the current model. Reset the patience counter.
6. If not improved, increment the patience counter.
7. When patience hits `patience` (default 10), return `False` from `_on_step()`. SB3 terminates training. The best-so-far model is already on disk.

Key invariant: the validation Sharpe is NEVER used as a training reward — only as a checkpoint-selection signal. The agent's gradients still come from whatever reward the env produces (DSR, log-return, etc.) on the train_only slice.

A per-window, per-seed JSON history file is also written: `models/agent_<algo>[_w<i>][_s<seed>].history.json`. It records `timesteps`, `sharpe`, `improved`, `best_so_far` per evaluation point — useful to inspect the validation trajectory after a run.

## Why this design

- **train_only**: large enough for the policy to converge. With 6-year train and 10% validation, you get ~5.4 years of gradient signal per window.
- **validation**: a separate period for monitoring, so the ES decision is based on data the policy isn't currently overfitting to. Crucial when the reward function is noisy (DSR can spike on individual days; without validation you'd save the wrong checkpoint).
- **eval**: completely unseen until stage 3. Used only to report what an investor following the strategy in real time would have experienced.

## The `val_fraction` knob — what changes when you increase it

`early_stopping.val_fraction` is a float in (0, 1) that controls the train_only/validation split inside each window. Default: 0.1.

| val_fraction | val length per window | train_only length | Effect |
|---|---|---|---|
| 0.05         | ~75 days  (~3.5 months) | ~95% of train     | Smaller val → noisier Sharpe estimate → ES decisions become unreliable. Risk: stopping on noise rather than real plateau. Faster to evaluate (less data to roll through each eval). |
| 0.10 (default) | ~152 days (~6 months) | ~90% of train     | Reasonable compromise. Sharpe estimate is stable enough; train_only still has ~5.4 years of data. |
| 0.20         | ~302 days (~14 months) | ~80% of train     | More stable Sharpe estimate → ES decisions more reliable. Cost: less training data (~4.8 years remaining). For walk-forward windows that already have only 6 years of train, this is the upper limit before train_only gets too thin. |
| 0.30         | ~454 days (~21 months) | ~70% of train     | Very stable val Sharpe but train_only shrinks to ~4.2 years. The policy has less to learn from. Often hurts more than it helps. |
| 0.50         | ~756 days (~3 years)   | ~50% of train     | Train_only = 3 years of data. The PPO model probably underfits — it never sees enough state diversity. Not recommended. |

### When to raise val_fraction

- Validation Sharpe is very noisy run-to-run, ES stops at inconsistent timesteps across seeds → larger val gives more stable signal.
- Stage 3 results swing wildly between two re-runs with the same seed → may indicate ES is picking different "best" checkpoints due to noise → larger val helps.

### When to keep it small

- Training data is precious (you have only a few years of data to work with).
- Validation Sharpe trajectory is already smooth (visible in `models/*.history.json`).
- You're using shaped rewards like log_return that produce stable Sharpe estimates even on small slices.

### Bounds we enforce

`split_train_validation()` raises if `val_fraction` is outside (0, 1) — that's a hard error. It also rounds to at least 1 day of validation (so val_fraction=0.0001 with 1512 train days would still give 1 val day rather than zero).

The factory will also print an informational message during stage 2 startup when `val_fraction` is below 0.05 or above 0.30, since both ends tend to hurt more than help.

## Effect on stage 3

Stage 3 doesn't care about `val_fraction` at all. The eval slice for each window is determined entirely by `walk_forward.auto.eval_years` (and `data.trade_end_date`). Changing `val_fraction` only changes WHICH checkpoint within the window gets saved by ES; the eval period itself is unchanged.

This means you can A/B test `val_fraction` cleanly:
- Run stage 2 with `val_fraction = 0.10`. Look at stage 3 metrics.
- Run stage 2 with `val_fraction = 0.20` (everything else fixed). Look at stage 3 metrics.
- Compare. If the stage 3 result improved, the larger val was picking better checkpoints.

## Where in the code

`utils.py`:
- `expand_walk_forward_windows(config)` generates the outer window list.
- `slice_by_dates(df, start, end)` slices a DataFrame to a date range and re-factorises the integer index.
- `split_train_validation(train_df, val_fraction)` does the inner split.
- `ValidationSharpeCallback(BaseCallback)` is the SB3 callback that runs validation rollouts.

`02_train.py`:
- `train_one(...)` calls `split_train_validation` when `early_stopping.enabled = true`, builds the callback, and attaches it to `model.learn()`.
- `train_walk_forward(...)` is the outer loop over windows.

`03_backtest.py`:
- `predict_one(...)` and `predict_walk_forward(...)` use the eval slice and never touch the train_only or validation slices.

## Summary of the no-leakage invariants

For every walk-forward window `i`:
1. The model never sees data from `eval_start[i]` or later during stage 2.
2. The validation slice used by ES is strictly inside `[train_start[i], train_end[i])`.
3. The eval slice used by stage 3 is strictly `[eval_start[i], eval_end[i])`, which is AFTER `train_end[i]`.
4. Different windows have different (train_only, validation, eval) triples — window i's eval is not used by window j's training.

The whole pipeline is leak-free in the strict sense: at no point does a model receive information about data dated later than its own train_end.
